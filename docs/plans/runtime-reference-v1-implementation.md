## Fixed prospective profile and exact schemas

All new schemas have exact keys/types; bool is never an integer. Canonical JSON is UTF-8, sorted object keys, separators `,`/`:`, `ensure_ascii=False`, `allow_nan=False`, no trailing newline. Reject duplicate keys, noncanonical encodings, unknown fields, nonfinite numbers and invalid Unicode/surrogates. Hash the canonical *actual bytes*, never a reconstructed permissive parse. Pure validators accept values/bytes supplied by callers and do no filesystem IO.

`PROFILE` is one immutable literal in the new helper, identified by `profile_id = memory-source-runtime-profile-v1-proposed` and `profile_sha256 = sha256(canonical(PROFILE))`. It is not an accepted actual-execution policy. Record the entire following table in that literal; callers cannot supply alternative limits.

| Dimension | Exact bound |
|---|---:|
| Complete roots | 1–16 |
| Outside-root standalone regular files | 0–1024 |
| Global regular files, roots plus standalones | 1–32768 |
| Global census entries | 60000, counting each selected root directory, every descendant directory and every regular file/standalone |
| Global regular-input bytes | 16 GiB, including all selected root/standalone files |
| Per-file bytes | 0–2 GiB |
| Per-root bytes | at most 16 GiB and subject to the single global sum |
| Manifest bytes / nodes | 1–16 MiB / 1,000,000 |
| Recipe bytes / nodes | 1–64 KiB / 8192 |
| Completed-ledger bytes / nodes | 1–256 KiB / 32768 |
| Inline cumulative charge reference bytes / nodes | at most 8192 bytes / 64 nodes, charged inside freeze and every emitted copy |
| All new JSON depth | 32 |
| UTF-8 path bytes / component bytes | 4096 / 255 |
| Root-relative path depth | 32 components |
| Other strings | 1024 UTF-8 bytes unless digest/ID/enum has its tighter rule |
| Ledger operations / extra retained files | at most 1024 each; serialized bound remains authoritative |

Selected runtime 16 GiB is distinct from recipe/manifest/ledger/evidence storage: every byte of those records also enters the external physical preparation ledger, bounded as above, and never enlarges the 640 MiB attempt output allowance. The extra retained files listed by the ledger are at most 16 MiB total and individually at most 1 MiB; they are preparation evidence, not a second runtime namespace or a place to hide runtime copies. A copied full runtime needs its own manifest-described actual paths and still fits the global runtime bounds or refuses.

Absolute paths must be canonical POSIX, non-root, no `//`, trailing slash, traversal, backslash, colon, controls, NUL, or empty component; reject symlink/special/hardlinked regular leaves during custody. Relative paths use the same rules without leading slash, plus the depth bound. Metadata paths/root paths must fit their total UTF-8 bounds. `sha256` is exactly 64 lowercase hex; operation/preparation IDs are canonical UUID hex. File records permit size zero. Manifest/recipe/ledger descriptors require positive bounded size.

Use these exact record definitions:

- `Descriptor = {path, size_bytes, sha256}` with a canonical absolute path. Internal `File = {path, size_bytes, sha256}` uses a canonical relative path.
- `RuntimeReference = {schema, profile_id, profile_sha256, load_policy, recipe, manifest, ledger}`; schema `memory-source-runtime-reference-v1`; the last three fields are descriptors. `load_policy` is exactly `retained-unqualified-v1` everywhere in this prototype, never a boolean and never inferred from `-B`.
- `Recipe = {schema, preparation_id, profile_id, profile_sha256, load_policy, intended_roots, intended_standalones, method}`; schema `memory-source-runtime-recipe-v1`; roots/standalones are sorted absolute paths; `method` is the exact descriptive string `externally-prepared-complete-runtime-input`. The recipe is a pinned statement of intended preparation, not proof it ran or an executable recipe. No future manifest/ledger/freeze hash appears here.
- `Manifest = {schema, preparation_id, profile_id, profile_sha256, load_policy, recipe, roots, standalones, pins}`; schema `memory-source-runtime-manifest-v1`; `recipe` equals reference.recipe. `roots` is sorted by root path, each exactly `{root, kind, files, directories}` with kind `complete`, sorted distinct `File` records and sorted descendant directory relative paths (root is implicit and counted once). `standalones` is a sorted distinct list of absolute `Descriptor` records outside all selected roots. `pins = {python_alias, python_elf, owner_source, pyvenv_config, required_sources}`; alias is a canonical absolute string, other scalar pins are exact descriptors and required_sources a sorted descriptor list of at most 64. Manifest contains no ledger or freeze hash.
- `Ledger = {schema, preparation_id, state, recipe, manifest, baseline, operations, retained_files, runtime_input_bytes, external_record_bytes, totals, cumulative_charge_reference}`; schema `memory-source-runtime-preparation-ledger-v1`, state `completed`. `recipe`/`manifest` equal the reference descriptors. `baseline = {accounting_id, project_cpu_ns, memory_cpu_ns, evidence}`; `accounting_id` is a UUID, evidence a Descriptor for independently retained earlier accounting. `operations` is sorted by operation_id and contains `{operation_id, outcome, memory_cpu_ns, evidence}`; outcome exactly `completed` or `failed`, evidence a Descriptor for independently completed operation accounting. All operations in this preparation belong to memory and therefore project equally. `retained_files` is the sorted complete set of additional accounting/preparation evidence descriptors, including baseline/operation/cumulative-reference evidence; none overlaps runtime, recipe, manifest or the ledger path. `totals = {project_cpu_ns, memory_cpu_ns}`. CPU ns integers are nonnegative and bounded by 86400*10**9/project and 43200*10**9/memory; memory cannot exceed project. Unknown/incomplete CPU cannot appear as zero; missing evidence, unknown state or overflow refuses. State completed describes the record's declared preparation snapshot, not authenticated whole-project accounting or its own publication tail.
- `CumulativeChargeReference = {evidence, project_cpu_ns, memory_cpu_ns}` is a small inline binding with no separate schema/service. `evidence` is an independently supplied cumulative-accounting Descriptor; the two exact integers equal Ledger.totals. The V4 freeze carries this identical binding as `prior_charge_reference`. The prototype checks descriptor identity and numerical consistency only; it does not interpret the external collector's evidence as authority or authenticate global completeness from caller JSON. Do not add publication supplements or recursive accounting records.

For Ledger, `runtime_input_bytes` is the sum of unique manifest file/standalone paths. `external_record_bytes` is recipe.size + manifest.size + sum(retained_files sizes); it deliberately excludes the ledger's own bytes. The complete described external input cost adds reference.ledger.size. Do not make the ledger contain its own digest or a guessed self-size. The ledger descriptor in the outer reference provides that final size/hash. Equal descriptors for one physical path deduplicate only identical pins; a different actual path is another physical copy even with equal content. Reused evidence descriptors at one exact path count once but do not permit two operation IDs to claim the same observed execution as independent work. This is the described artifact inventory, not proof no other preparation bytes exist.

## Accounting graph, CPU consistency and authority

The directed binding order is `recipe -> manifest -> completed external ledger (+ independent cumulative charge reference) -> V4 freeze`. The freeze holds the final reference, identical cumulative charge reference and job. A completed ledger has no freeze hash and no self-descriptor; the manifest has no ledger hash; the recipe has neither. The independent charge evidence must not hash-bind the as-yet-uncreated final ledger or future freeze. This is a bounded per-preparation ledger plus one cumulative baseline, not a global database/history service.

Each represented execution has one unique operation ID, one declared complete enclosing charge and one external accounting evidence descriptor. Never add descendants to an inclusive parent charge. Distinct attempts/failures retain distinct IDs and charges, even when they produce equal manifests. Baseline plus ledger-operation sums must exactly equal ledger totals and the independently supplied cumulative-reference totals, with preparation operations added equally to memory/project. Duplicate IDs, reused evidence under different IDs, incomplete declared accounting, negative values, overflow or memory>project refuse. These arithmetic checks do not establish authenticity, globally complete coverage, or the truth of a caller's completed label; collector authority remains UNQUALIFIED.

V4 retains `prior_cpu = {project_seconds, memory_seconds}` for existing monitors, but requires actual finite nonnegative Python floats, no integers/bools/NaN/infinity. Convert each exact cumulative-reference integer N ns to the *least binary64 float not less than N/10**9*. Compute comparison using `float.as_integer_ratio()` and integer cross multiplication; if nearest conversion is below the rational, take `math.nextafter(x, math.inf)`. Require exact equality to this canonical float, including positive zero only; no epsilon and no `int(seconds*1e9)` reconstruction. For fixed allocation admission use integer `prior_ns + 1800*10**9 <= lane_ns`, so upward representation rounding neither gains budget nor creates a false exact-boundary failure. Existing float live monitors remain conservative containment; actual final CPU acceptance still requires external lifetime reconciliation. V3's old prior-CPU validation is unchanged.

Ledger generation cannot observe its own complete publication/process-exit CPU. Ledger publisher, observer and freeze-creation tails eventually require an independently reconciled external accounting/lifetime backend. This plan does not implement that backend or manufacture a later self-attested supplement to claim closure. At actual adoption all preparation through freeze/startup must be included exactly once in prior accounting or the externally measured attempt interval, with an explicit nonoverlapping cut. The prototype always reports this backend UNQUALIFIED/unresolved and refuses actual execution even when all byte bindings and internal sums agree. These open authority questions do not prevent implementing the schema and arithmetic now.

## Namespace and handle contract

`validate_runtime_reference(value: dict) -> dict` validates/copies the exact reference with no IO. `validate_runtime_manifest(raw: bytes, reference: dict, *, required_roots: tuple[str, ...], required_pins: dict, output_root: str) -> dict` checks bytes/hash/schema/profile/caps/coverage/pin equality and returns a private normalized copy. `validate_preparation_recipe(raw: bytes, reference: dict, manifest: dict) -> dict` checks its binding and intended paths exactly. `validate_preparation_ledger(raw: bytes, reference: dict, manifest: dict, recipe: dict, *, prior_charge_reference: dict | None = None, prior_cpu: dict | None = None) -> dict` returns derived byte totals and integer CPU totals; reference/prior must be either both present or both absent. Parent requires both; child validates the ledger's own declared totals and byte bindings. Every returned accounting result explicitly has `accounting_authority_qualified: false`.

`hold_runtime_manifest(reference: dict, *, required_roots: tuple[str, ...], required_pins: dict, output_root: str, deadline: float, check: Callable[[], None]) -> RuntimeHandle` returns a one-shot context manager. It exposes `recheck() -> None`, `descriptor(path: str) -> dict` (one exact descriptor copy), `summary() -> dict` (fixed fields below), and `accounting(*, prior_charge_reference: dict, prior_cpu: dict) -> dict` (Task 1's checked integer/byte totals, <=2048 serialized bytes, authority always false). No FD escape, arbitrary read/import API, authority-producing boolean, registration generator or implicit root discovery. Constructor/reference validation does no payload IO; `__enter__` holds and bounded-reads recipe/manifest/ledger, validates them, then acquires regular files, listed preparation evidence and exact namespaces. Reads/hashes/rechecks call `check` and the unchanged absolute deadline. A parse/size/cap/custody/close failure poisons all subsequent operations; final recheck occurs before release. Partial acquisition closes all held FDs. Empty complete roots are permitted and held/censused even if they contain no files; global regular-file minimum still applies.

Implement private `_SourceNamespaceFiles` over the existing parameterized `_HeldFileCore`, with local exact directory topology and ancestor-edge logic derived from `puck_retained_installation.py`. Use new profile limits explicitly, not `HeldInstalledFiles.__init__`'s old 3 GiB constructor. Maintain full identity at/below selected roots and edge identity above them. Hold selected empty directories; census exact names/types; reject links, special files, unexpected/missing members, global inode aliases, replacement and change/restore. A stat-only site observation reported ~7.6 billion bytes: it demonstrates why the old per-holder policy cannot be silently reused, not that this new holder will fit FD/time/RSS limits. No root sharding, paging or weakened rechecks.

Required roots come from the source executing layout, not the manifest: exact `ROOT/src`, `ROOT/scripts`, `ROOT/paper/studies/change_audit_v1`, executing venv site-packages and base-interpreter stdlib. Normalize required nesting by retaining the outer required root if it contains another required root; this is deterministic complete coverage, not caller-selected trimming. Selected roots must cover these in full, may not overlap each other, and may not overlap output or recipe/manifest/ledger/evidence paths. Explicit additional roots/standalones must be declared before freeze and fit global limits; native standalone selection is not native discovery proof. Python ELF, owner, `pyvenv.cfg`, parent, new helper, numeric helpers and CPU-helper-containing parent source must all resolve to manifest records. Preserve existing assets/input custody obligations; do not drop old immutable dependencies when migrating a job.

Every underlying file appears once, either inside a root or as an outside-root standalone. Redundant semantic pins must equal that record exactly and do not add physical/count charges. Preserve the existing explicitly pinned Python alias-chain exception, checked separately with `_alias_identity` semantics; it grants no symlink allowance inside selected roots. Old `.pyc/.pyo`, headers and `.pth` files remain fully represented and held as current bytes. This profile grants none of them import/startup authority, even when authenticated; `-B`/pycache-prefix/JSON labels cannot change that.

`summary()` exact fields: `{schema, manifest_sha256, profile_sha256, load_policy, root_count, file_count, directory_count, input_bytes, current_bytes_checked, runtime_qualified, source_qualified, execution_authorized}` with schema `memory-source-runtime-current-bytes-v1`; current_bytes_checked true only after a successful recheck, other three flags always false. Canonical summary <=2048 bytes. No per-file/FD roster appears in it. Its creation/emission CPU and bytes count in the attempt.

`accounting()` returns exactly `{runtime_input_bytes, external_input_bytes, project_cpu_ns, memory_cpu_ns, accounting_authority_qualified}`; external_input_bytes includes runtime plus all described recipe/manifest/ledger/retained-evidence bytes, and accounting_authority_qualified is always false. It rechecks before and after using the held normalized records, checks the supplied cumulative-reference/prior-float match, and does not expose raw records. Validators and the handle share this arithmetic implementation.
