## Decision and accounting boundary

Option B is not inherently accounting evasion. An independently retained runtime input can be referenced by an attempt without reproducing its full roster in every output. Proposal lines 50–58 correctly make this a new contract, retain reproducibility dependence, charge real copies and preparation, prohibit retroactive “preexisting” labels, and leave emitted evidence in the combined 1 MiB envelope. This changes the interpretation of support bytes in `docs/plans/memory-numeric-preservation-v2-implementation.md:19–22`; it cannot be presented as old V2 compliance.

Approve the following *design boundary*, not adoption or actual feasibility:

- A completed, immutable shared artifact predates the source freeze. Its complete physical runtime, manifest, provenance, preparation/verification material, and actual copies are retained and charged in a separate, explicitly bounded preparation/full-project ledger. Equal content hashes do not erase copies. Reference reuse does not repeat an already accounted physical-path charge.
- All preparation/validation CPU, including failures, enters the existing memory/project accounting once per actual execution. During-attempt parsing, hashing, census, rechecking, parent/child acquisitions and teardown remain in that attempt's CPU/wall/RSS envelope. A shared artifact never amortizes away repeated validation work.
- Every attempt-created descriptor, provenance/control/custody/result record and physical copy remains charged to the unchanged combined 1 MiB metadata envelope. Full roster/holder-state serialization into controls is not exempt. Runtime input exclusion is fixed by the reviewed version and pre-freeze ledger, never inferred from location outside `controls/`.
- Preserve raw512 + SNP16 + candidate32 + controls8 + atomic8 + headroom64 = 640 MiB, wall900/CPU1800/8 GiB runtime memory/6 GiB free-space floor and project24h with audit1h/memory12h/puck5h/navigation4h/final2h. Source-work/cleanup sublimits remain unchanged. See `docs/plans/memory-source-preservation-v2.md:79–115,191–207` and `scripts/qualify_memory_family_source_v2.py:33–38,737–746`.
- The proposed 32768 files/60000 entries/16 MiB manifest is a **new, unadopted profile**. No current installation is known to fit. The supplied rough 31964 required-root file count would leave only 804 file slots before configs/native additions; this arithmetic is not a qualified inventory or a byte/FD/time feasibility result. The proposal's site-only 3099 remaining slots at line 42 must not be used as the complete-runtime margin.

## Load-bearing findings and minimal fixes

### 1. Specify the parent/child custody handoff; a parent handle does not cross exec

**High priority.** Proposal lines 35–37 say to replace owner identity checks with a held handle, but do not state how the owner gets it. The actual owner is a new interpreter invoked with only job path, digest and outcome path (`scripts/qualify_memory_family_source_v2.py:498–513`). `run_source` invokes `_check_identity` before loading and passes a callback that repeats it (`scripts/memory_family_source_runtime_v2.py:396–407`); the old checker directly indexes `immutable.closure` (`:213–240`). A parent Python handle cannot supply that child callback, and the old callback cannot operate on a V3 reference.

Minimal fix: state that V3 parent and owner each acquire a process-local context from the same exact immutable reference under the same externally established isolation binding. Parent custody lasts through parent finalization; child custody encloses engine use, reports and its final checks. Both acquisitions and all rechecks are charged. The child uses the existing absolute admission deadline, never a fresh interval. The new helper exposes context-manager close semantics plus `recheck`, immutable descriptor lookup, and bounded summary; no serialized live handle, FD transfer protocol, or generic RPC is needed. An alternative division of custody is possible, but must explicitly retain equivalent child identity checks rather than silently dropping them. An unavailable binding refuses V3 execution.

Also spell out the compatibility matrix: V2 job/V3 freeze remains on the exact inline implementation; V3 job/V4 freeze uses only the reference implementation; mixed pairs refuse. Identify whether parent-admission, preparation and result schemas stay structurally compatible or receive explicit new versions. Existing preparation/result labels are V3 (`scripts/qualify_memory_family_source_v2.py:238–241,631–634`) and parent admission is V2 (`scripts/memory_family_source_runtime_v2.py:174–183`); changing the job must not implicitly change what those labels promise. Preserve the 256 KiB job contract and combined metadata accounting, including the admitted job copy.

### 2. Replace the deferred bytecode ruling with an explicit prototype policy

**High priority.** Proposal line 40 includes old bytecode, while line 44 defers whether it can execute. Current V2 unconditionally rejects `.pyc/.pyo` (`scripts/qualify_memory_family_source_v2.py:295–297`), and its launch uses `-B` plus environment fields (`:126–134,511–515`). The Puck inert-cache rule admits exactly one named historical cache and rejects `.pth` (`src/palimpsest/puck_retained_installation.py:75–84`); it is not a policy for thousands of caches or startup hooks. `HeldInstalledFiles` itself grants no import/load authority (`:1–4`).

Minimal fix: make a pinned exact `load_policy` identity mandatory in the new profile/reference/freeze binding. For the first source prototype, represent retention of caches but keep execution inadmissible until a reviewed startup/load policy is bound. Unknown policy, a label such as “inert” without a binding, or `-B` alone must not admit execution. If executable authenticated caches are later selected, explicitly version that behavior and cover `.pyc`, `.pyo`, sourceless loaders, `.pth`/site startup and native delayed-load boundaries in that policy. If exclusion is selected, the external binding must enforce exclusion before affected imports. Do not build a new loader or delete caches as part of this format migration. Fixtures can prove rejection/dispatch behavior now; real startup evidence is an adoption gate later.

### 3. Make the manifest/ledger binding noncircular and accountably checkable

**High priority.** Proposal lines 36, 40 and 52–56 require a preparation/provenance descriptor and a separately frozen ledger but do not give the finite identity relationships or how the ledger relates to `prior_cpu`. Current freeze accounting has only project/memory scalar totals (`scripts/qualify_memory_family_source_v2.py:191–195,219–220`), and admission adds the full fixed attempt allocation to those totals (`:737–739`). Merely accepting a ledger digest cannot show that preparation was included exactly once. If manifest and provenance each hash-bind the other's completed bytes, the format also becomes impossible to construct.

Minimal fix: define a small acyclic graph. A completed preparation input/recipe record can precede and be bound by the manifest; a completed ledger then binds the finalized manifest and all actual retained preparation artifacts/copies; V4 freeze binds both manifest and final ledger. The ledger must not depend on the future freeze hash. Define exact schemas and bounded sizes for these records, preparation completion status, operation/accounting IDs, actual path/copy charges, failed-operation charges, and the cumulative project/memory totals that the freeze uses. Require independently reconciled totals; unknown earlier costs refuse actual admission. Preparation entries count once as executions, not once per artifact digest. A new source attempt refers to already charged preparation and adds its own measured work. An attempted second physical copy or newly emitted provenance is newly charged. This is a small ledger-reference validator, not a global accounting service.

Descriptor-only verification checks shape/identity bindings without opening the runtime manifest or ledger payload. Actual readback/reconciliation remains behind the existing gates. A pre-freeze temporal label alone is not proof of immutability or completed accounting. No real ledger or measured preparation budget is required to implement the exact schema and authored rejection cases.

### 4. Freeze all global resource dimensions, not only the three headline caps

**Medium priority.** Proposal line 42 defines global files/entries/manifest bounds, but leaves an exact source profile's root count, aggregate input bytes, standalone-file aggregate, provenance/ledger read bounds and parser structural limits unstated. The reused mechanisms have different limits: `HeldInstalledFiles` permits 5000 directories and 3 GiB per holder with 1 GiB per file (`src/palimpsest/puck_retained_installation.py:89–109`); Puck's dependency policy has 16 GiB globally and 2 GiB per file (`src/palimpsest/puck_dependency_files.py:29–35,245–266`). The latter limits do not automatically carry into a new adapter. Multiple holders must not multiply the intended global byte ceiling. `AdmissionInputs.read_json` has an 8 MiB cap (`src/palimpsest/puck_retained_installation.py:52–69`), so it is not a drop-in 16 MiB manifest reader.

Minimal fix: enumerate an exact closed prospective policy containing root/standalone counts, global file/directory-entry/input-byte bounds, per-file and per-holder bounds, manifest/provenance byte and JSON depth/node/path bounds, and whether selected root directories count as census entries. Use one bounded reader/parser for the manifest, held before parse, rather than raising unrelated existing APIs' limits. Select a fixed prototype policy explicitly or keep the profile unadopted and execution closed; do not accept caller-supplied numeric overrides. Enforce globals across all roots/standalones before acquisition and during census. Keep lower holder limits effective and do not shard roots to defeat them.

**New supplied stat-only observation:** the parent reports `runs/numeric-v2-canonical-53ab035/environment-size-metadata-observation.json` records 29669 regular site-package paths, 7,601,540,493 apparent bytes, largest leaf `torch/lib/libtorch_cuda.so` at 1,022,772,113 bytes, and zero symlink files. This reviewer did not independently open that observation or any represented payload. The supplied total exceeds the existing holder's 3,221,225,472-byte (3 GiB) limit, while the largest reported leaf is below 1,073,741,824 bytes (1 GiB). Thus direct wrapping of `HeldInstalledFiles` cannot represent that reported root under its existing policy. A proposed 16 GiB global ceiling does not override a 3 GiB local one. This establishes a policy mismatch from the supplied metadata, not qualified byte inventory, inode custody or runtime feasibility.

Minimal narrow reuse alternative: make the new source helper contain a private explicit source-policy holder built from the already parameterized `_HeldFileCore` (`src/palimpsest/puck_execution_files.py:53–87`) and the exact selected-tree/empty-directory checking semantics of `_AdmissionFileCore` and `HeldInstalledFiles` (`src/palimpsest/puck_retained_installation.py:16–45,89–134`). Preserve selected-root full identity and ancestor-edge identity. Reuse or locally compose that small checker; do not inherit the old constructor and quietly replace its constants, monkey-patch its methods, change old Puck source/pins, or split the site root. Fix new source-profile limits in reviewed source, never caller-supplied overrides. An explicitly proposed source holder bounded by a global 16 GiB total (with chosen per-root bound no greater than that global bound, and a stated per-file limit) is source-implementable; this review does not adopt that profile. All manifest, standalone, preparation-record and cross-root aggregate checks still apply. No new import/lease framework is needed.

Held-file custody retains one FD per selected leaf plus directories (`src/palimpsest/puck_execution_files.py:241–265`), and recheck hashes every entry (`:271–280`). Declare that finite resource cost and fail closed on FD exhaustion; do not promise large-runtime fit or add descriptor paging/recheck shortcuts in this migration. The unchanged full-runtime resource envelope remains the adoption test.

### 5. Define equality of redundant pins and the exact complete namespace

**Medium priority.** Proposal lines 36 and 40 retain Python/owner pins while adding a complete manifest. Unlike V2's distinct descriptor list (`scripts/memory_family_source_runtime_v2.py:125–134`), the complete `scripts` manifest necessarily includes `owner_source`; Python ELF/native/config identities may also be separately referenced. An implementation must not either reject intentional repeated identity references or count them as two physical files. The current parent accepts required prefixes as covered by selected roots and separately requires `pyvenv.cfg` (`scripts/qualify_memory_family_source_v2.py:386–400`).

Minimal fix: one canonical physical file record per path in the manifest. Python/owner/config/native references point to that record or are explicitly outside-root standalone records; repeated semantic pins must match size/hash exactly and do not create extra file-count/storage charges. Manifest, preparation records, runtime roots and output must have an explicit global nonoverlap/alias policy. A file cannot occur both as a standalone and inside a complete root. Preserve the intentionally allowed Python alias chain as a separately pinned alias, not a general permission for links in runtime roots.

Required roots are fixed by the source policy/executing layout and compared exactly for coverage; callers cannot downgrade a required full prefix to a few standalone files. Include every directory including empty ones. Root kind must distinguish complete namespace custody from selected standalone bytes, and neither kind asserts complete native discovery. Zero-byte regular runtime files must be representable (`_HeldFileCore` allows size zero at `src/palimpsest/puck_execution_files.py:79–81`), even though the old top-level immutable descriptor helper requires a positive size (`scripts/memory_family_source_runtime_v2.py:90–95`). Define the new internal file-record schema explicitly instead of reusing that helper blindly.
