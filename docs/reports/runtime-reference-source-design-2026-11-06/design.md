# Runtime closure feasibility: prospective source contract

Status: SOURCE-ONLY DESIGN, not implementation, registration, input qualification, freeze, GO, or cap approval. Analysis targets the assigned `53ab035` source state. Only the named public sources and retained directory-name observations were inspected. No runtime/model/raw/SNP payloads were opened, imports/tests/native/research processes invoked, installation changed, or receipt manufactured. The actual source CLI stays closed. Whole-parent startup/isolation and lifetime/tail design belong to the parallel lifetime plan; this document specifies only the closure interface that design must satisfy.

## Decision

The current source contract cannot admit the observed shared installation unchanged. The smallest plausible successor replaces the inline runtime roster with a descriptor for a separately prepared, immutable, complete runtime-input artifact, while retaining complete file and directory membership and independently reviewed native/load closure. That requires a **new source contract version and an explicit accounting ruling**. Externalizing JSON by itself neither qualifies a runtime nor makes its metadata free.

Do not raise the V2 owner's 4096-entry cap, relax V3 freeze semantics, drop headers/bytecode, filter installed packages by imports, delete caches, or split the roster into chunks to evade a global ceiling. Do not import the Puck qualification apparatus as if it already authorizes this source stage. If the reviewed meaning of “all support/control metadata” includes the full external runtime manifest in the source's combined 1 MiB envelope, this installation remains blocked: the proposed descriptor path does not solve that interpretation.

* `docs/plans/memory-source-preservation-v2.md:65-76,171-214` and `docs/plans/memory-numeric-preservation-v2-implementation.md:19-22,50-68` preserve combined metadata 1 MiB, raw 512 MiB, sole SNP 16 MiB, candidate 32 MiB, and stage peak 640 MiB. ## Minimal prospective files and interface

This is one focused contract migration, not a replacement runtime/import framework. No proposed numeric ceiling below is adopted by this document.

1. Add `scripts/memory_source_runtime_closure_v1.py` for one exact external-manifest schema and adapter. Its public surface is `validate_runtime_reference(reference)` (metadata only) and `hold_runtime_manifest(reference, *, required_roots, deadline, check, isolation_binding)` (execution-admission only), returning a one-shot handle with `recheck()`, exact descriptor lookup and a bounded manifest-descriptor/count summary. It must not expose an authority-producing boolean, auto-discover roots, create registrations or return a synthetic qualification receipt.
2. Introduce an explicit `memory-family-source-job-v3` branch in the existing owner module, replacing only `immutable.closure` with `immutable.runtime_manifest`. Keep Python alias/ELF and owner source pins, all source-case restrictions and research limits. The reference binds canonical absolute manifest path, exact size, SHA-256, manifest schema and an independently pinned preparation/provenance record descriptor. Keep the whole job at 256 KiB. Reject old/new mixed schemas; V2 remains exact and unchanged, with no fallback.
3. Introduce `memory-family-source-freeze-v4` in the existing parent: bind the V3 job, reviewed closure policy identity, external-input classification and complete required roots. Keep the whole freeze at 1 MiB. Replace the inline-roster assumptions in `_bind_inputs`, `_bind_runtime_namespace` and owner identity checking with the held external handle. Required parent/new helper/owner/stdlib/environment/venv-config membership must still be explicit. Keep `verify` descriptor-only; execution must still refuse at unresolved authority gates before opening runtime or protected payloads.
4. Add focused authored tests in `tests/test_memory_source_runtime_closure_v1.py` and extend existing source-owner/parent metadata/accounting tests. Update `docs/plans/memory-source-preservation-v2.md` with the reviewed version/accounting boundary. No numeric codec, raw auditor, source case, namespace coverage, trust pin or GO change follows automatically.

Manifest content is a complete sorted root-relative file roster with size/SHA-256 and sorted directory inventory, root kind and identity, Python/venv/source/native boundary descriptors, plus provenance bindings. Include all original bytecode and headers. Relative paths reduce repeated text but do not remove any identity or byte charge. The manifest itself must be held and outside all runtime roots and fresh output, and overlapping roots/aliases must be rejected globally. Explicit standalone configuration/native files may be separately listed without pretending their entire parent directory is a complete selected prefix. No paths can be implicitly selected on first observation.

For the first proposed profile, use a **single global** ceiling of 32,768 files and 60,000 census entries across complete roots and standalone files, with external manifest at most 16 MiB, drawing from existing dependency bounds. An adapter around `HeldInstalledFiles` can reuse complete-directory identity checks, subject to its stricter per-holder byte/directory limits; globally enforce bounds rather than multiply them per root. This is a proposed versioned software profile, an explicit increase from source V2, and requires review before implementation/admission. The observed site name count leaves only 3,099 file slots for stdlib/source/config/native inputs, so even this profile is **not known to fit**. Do not switch automatically to 40,000, shard manifests or raise byte/directory ceilings on failure.

The external isolation binding must establish the complete manifest-selected runtime before any affected import/exec and keep it immutable through final recheck/teardown. The adapter's ordinary descriptor checks are evidence under that binding, not a substitute for it. Reusing `HeldDependencyNamespace` directly would additionally require resolving its shorter policy lifetime, signal-owner constraints and metadata copying; do not solve those by changing its constants. The separate lifetime plan owns the operating-system mechanism. Bytecode may be retained as accounted input but its actual importability must be ruled on explicitly: `-B` suppresses writes and does not prove old cache bytes cannot be loaded. A reviewed startup/load policy must bind whether caches are excluded from execution or authenticated as executable input. No cache deletion or quiet loader change is proposed here.

## Accounting ruling that must precede implementation

There are two distinct possible contracts:

**A. Existing all-support interpretation.** The complete runtime manifest is indispensable support metadata for this source artifact, hence its full physical bytes join the combined 1 MiB overhead. Keeping it outside the output directory does not change that. The observed site-packages manifest alone exceeds the bound by the lower-bound argument above. The honest result is BLOCKED under this interpretation. There is no proven compliant runtime in this review. A tiny descriptor cannot substitute for counting the required support bytes.

**B. Prospective shared-runtime-input contract.** A separately prepared runtime artifact, with immutable manifest and provenance, is treated like the preexisting executable/package bytes: an external input reused by attempts, rather than newly created attempt evidence. Its complete physical bytes and manifest/provenance copies count once per actual physical path in a separately frozen preparation/full-project storage ledger; all preparation/validation CPU still counts in the applicable research/full-project accounting, including failures. Reading/hash/parse memory and CPU during an attempt remain in that attempt's measured runtime envelope. The attempt's complete descriptor, policy identity, preparation-ledger reference and custody/result records count in the unchanged 1 MiB combined metadata envelope, along with every other emitted control. Every actual copy counts separately.

B can be a coherent **new-version accounting definition**, because the measured artifact is the new source output and its runtime is an independently retained input; it is not established by current V2 text/code. Independent review must affirm that boundary and its reproducibility/provenance obligation. The source result must say it depends on that retained external artifact; it is not standalone, and descriptor presence proves neither availability nor custody. Full manifest, preparation history and verification material must remain available by immutable identity for independent source qualification. A lost/mutated external artifact blocks that qualification even when numeric raw-backed equality remains a separate fact.

No manifest created during this stage, copied under `controls/`, regenerated per attempt, or needed as newly emitted custody evidence can be relabeled “preexisting” to avoid a charge. A future separately authorized preparation step can create a shared artifact only with its own bounded storage/CPU/failed-attempt accounting and immutable completion before the source freeze; moving a current stage file elsewhere does not retroactively do this. There is currently no such qualified artifact or separately frozen preparation budget in this analysis. Existing 24h project/12h memory lane ceilings are not increased or reset. Installation and artifact storage feasibility remain unknown.

Under B the unchanged simultaneous stage reservation remains raw512 + SNP16 + candidate32 + controls8 + atomic8 + headroom64 = 640 MiB, with the **stricter** combined metadata 1 MiB applying across eligible controls/candidate metadata/reserves. Neither 8 MiB controls nor 64 MiB headroom is an extra metadata allowance. Freeze/job duplication and every descriptor/provenance/terminal byte must be measured together before admission. If they exceed 1 MiB, refuse. No claimed fit or qualification is made here.

## Authored acceptance cases for the next source plan (not run)

* Schema/size boundaries: unchanged V2 rejects external references; V3 rejects inline/mixed/unknown fields; V4 freeze binds exact schema/profile/reference hashes; 256 KiB job and 1 MiB freeze boundaries independently enforced. Metadata-only verification never opens the referenced runtime.
* Completeness: authored >4096-file fixture can be represented only by the explicit new policy; omitted header, old bytecode, empty directory, source helper, `pyvenv.cfg`, stdlib leaf and native dependency each refuse. Extra files/directories refuse. Combined global 32,768/60,000 ceilings and each stricter adapter limit refuse one over, including cross-root totals.
* Identity/custody: manifest hash mismatch, duplicate JSON/path/root, symlink/hardlink aliases, cross-root inode alias, path replacement, content change-and-restore, selected empty-directory churn and new sibling namespace entry poison the handle. Unrelated ancestor churn follows the reviewed existing retained-installation boundary. Missing or expired external isolation binding never admits runtime use.
* Bytecode/load boundary: retain and hash authored cache/header bytes; exercise the selected startup policy without a real dependency/model runtime. Test that an executable cache cannot bypass the pinned policy. Passing this fixture is not evidence of real Torch/stdlib startup behavior.
* Accounting: independently sum freeze/job/control copies, descriptors, all provenance summaries, receipts, numeric metadata and positive tail/atomic reserves. Exact combined 1 MiB passes only where all other constraints pass; one byte over refuses. A multi-MiB manifest emitted/copied by the attempt is fully charged and fails. Under approved B, a genuinely preexisting shared artifact is bound to its separate ledger and actual bytes/copies there; missing ledger/provenance refuses. Descriptor-only omission of a newly emitted manifest fails.
* Failure boundaries: drift/unknown custody, resource overrun or missing external artifact cannot produce a qualified terminal or restart a failed attempt. Existing closed-CLI tests stay closed without namespace, full-runtime, external lifetime, resource, prior-charge and exact GO evidence.

## External evidence still required

Directory-only observations cannot answer byte totals, links, special files, `.pth` startup effects, native lazy loads, FD needs or timings. The proposed 32,768 global profile may fail; report that exact failure rather than widening it.

Independent review must supply the manifest/provenance artifact identity and retained location, explicit A/B accounting ruling, complete preparation/full-project cost ledger, measured combined stage metadata/peak budget, and verification that holdings/hash/rechecks fit unchanged CPU/wall/memory/free-space limits. Pre-import immutable load binding and full-parent tail acceptance come from the separate lifetime work. Canonical historical/training namespace coverage and exact actual-stage GO remain separate mandatory gates. None is supplied by this design, existing Puck fixtures, or the running software suite.
